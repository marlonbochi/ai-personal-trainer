# Feature Specification: Translate the nutrition plan screen

**Feature Branch**: `translate-nutrition`
**Status**: Implemented (pending user review)
**Input**: "On the nutrition plan screen, translate whatever is not translated, e.g. abbreviations like F for fat, which in Portuguese is gordura (G), among other things."

## Audit (before)

| What the screen shows | Source | Problem in Portuguese |
|---|---|---|
| `P:` `C:` `F:` macro labels | hardcoded in `src/app/nutrition/page.tsx` | `F` (fat) should be `G` (gordura); no full name anywhere |
| Meal headings (`Breakfast`, `Lunch`, `Dinner`, `Snacks`) | object keys returned by Gemini, rendered raw | the prompt's example uses English keys even for `pt`, so the model returns them; the API test mock uses lowercase `breakfast` |
| Day pills and day heading | local maps keyed by English day names | a `pt` plan is keyed `Segunda-feira`: the pill falls back to `day.slice(0, 3)` and the heading stays in Portuguese when the UI is switched to English (and vice versa) |
| Dish names, ingredients, instructions | free text generated by Gemini | already in the language the plan was generated in; translating it would need another AI call, out of scope |

## User Stories

### US1 - Macro labels in the user's language (P1)
**Acceptance**:
1. Given the UI in Portuguese, each meal shows `P`, `C`, `G` (Proteína, Carboidratos, Gorduras), and the full name is available on hover / to screen readers.
2. Given the UI in English, each meal shows `P`, `C`, `F` (Protein, Carbs, Fat).

### US2 - Meal headings translated (P1)
**Acceptance**:
1. Given a plan whose meal keys are `Breakfast`, `lunch`, `Café da manhã`, `afternoon_snack`, `morningSnack`, `Snacks`... the heading shows the name for the current UI language ("Café da manhã" / "Breakfast", "Lanche da tarde" / "Afternoon snack", "Lanches" / "Snacks").
2. Given a meal key the app does not recognise, it is shown exactly as the model wrote it (no data loss).

### US3 - Days translated whatever language the plan was generated in (P2)
**Acceptance**:
1. Given a plan keyed `Segunda-feira` / `terca-feira` / `Monday`, the pill shows `Seg`/`Ter` (pt) or `Mon`/`Tue` (en) and the heading shows the full name in the UI language.
2. An unrecognised day key is shown as written.

### US4 - A generated plan is never lost to the storage format (P1)
Found while auditing the screen: `generate-nutrition` stored `btoa(JSON.stringify(plan))`, and `btoa` throws on any character above U+00FF. Gemini often writes en dashes ("–") or emoji, so the plan was not saved, the user saw "Failed to generate" and the screen kept showing "no plan". Same bug already fixed for workouts in 002.
**Acceptance**:
1. Given Gemini returns text with "–" or emoji, the plan is saved, the user is taken to `/nutrition`, and it survives a reload.
2. Given a plan stored by an older version (base64), it is still shown.
3. Given a corrupt stored value (not JSON, or JSON without `days`), the screen shows the empty state instead of crashing.

## Functional Requirements
- **FR-001**: Macro abbreviations and full names come from the locale files (`en` and `pt`).
- **FR-002**: Meal and day keys are matched case-, accent-, separator- and camelCase-insensitively, in both languages.
- **FR-003**: Unknown keys are displayed unchanged.
- **FR-005**: Plans are stored as plain JSON; reading accepts plain JSON and legacy base64 (shared `src/lib/storedPlan.ts`, also used by the workout plan).
- **FR-004**: Stored plans are not rewritten; translation happens at render time, so old plans and a language switch both work.
